# Canon EOS 4000D (Rebel T100 / 3000D), firmware 1.1.0

Status: **boots Canon firmware to the shooting screen (Canon GUI) headless; MENU and arrow keys work.**
CI smoke test: `ci/smoke.sh IMAGE 4000D` (step "4000D smoke test" in `.forgejo/workflows/ci.yml`), skipped
cleanly when the ROMs are not available.

| Item | Value |
|---|---|
| Model ID | 0x422 (`K422 READY` on the UART) |
| SoC / OS | DIGIC 4+ (ARM946E-S), DryOS 2.3 r58+p7, ICU firmware 1.1.0 (inner 1.9.5, built 2023-03-22) |
| Base model | 1300D (same platform): timers, MPU registers, SD, RTC chip select, UART, JPCORE quirks reused |
| Prior art | qemu-eos branch `2000d_test` (stephen-e, 2024, GPL-2.0): 2000D cloned from the 1300D with ROM0 disabled and the 600D/1200D MPU tables. This model follows the same approach |

## Memory map (as emulated)

| Range | What | Notes |
|---|---|---|
| `0x00000000-0x00000FFF` | ITCM | set by the bootloader (`FFFF00C4`) |
| `0x40000000-0x40000FFF` | DTCM | (`FFFF00D8`) |
| `0x00001000-0x0FFFFFFF` | RAM, 256 MiB | uncached mirror at `0x40000000` |
| `0xC0000000-0xCFFFFFFF` | MMIO | DIGIC 4 handlers |
| `0xF0000000-0xF7FFFFFF` | ROM0 | **not mapped**: the dump is a 4-byte bus pattern (`00 00 01 00` repeated), i.e. no chip fitted; its MD5 changes between dumps |
| `0xF8000000-0xF8FFFFFF` | ROM1, 16 MiB | NOR flash; mirrored up to `0xFFFFFFFF`. The 32 MiB dump holds two identical 16 MiB halves |
| `0xFE0C0000` | main firmware entry | `Firm Jump RAM to ROM 0xFE0C0000`; ROMBASEADDR `0xFF0C0000` is the same code through the mirror |
| `0xFFFF0000-0xFFFFFFFF` | boot block (hivecs) | ROM1 offset `0x10000` overlaid here, see below |
| `0xF8000000` / `+4` | boot flags | FIR / BOOTDISK, both 0 on this camera |

MPU protection regions set by the bootloader (from the `-d` log): `F8000000-F8FFFFFF` and `FE000000-FEFFFFFF`,
both 16 MiB, consistent with a 16 MiB flash.

## Fixes needed beyond the 1300D model

1. **ROM sizes.** ROM1 is 16 MiB (`rom1_size = 0x01000000`); a 32 MiB ROM1 made `check_rom_mirroring` abort
   ("unique 0x1000000 bytes repeated 0x2 times"). ROM0 is disabled (`rom0_size = 0`), otherwise the same check
   aborts on the bus pattern.
2. **Reset vector.** With a 16 MiB mirror, `0xFFFF0000` lands on ROM1 offset `0xFF0000`, which holds flash log data
   (`[CSRS] RealClearBusy...`), so the CPU hit an undefined instruction at `FFFF0004`. The bootloader is at ROM1
   offset `0x10000`: its vector table (`e59ff018` x8) points to `0xFFFF0040...`, so it is linked for `0xFFFF0000`.
   New model field `rom1_hivecs_offset` overlays that 64 KiB block at `0xFFFF0000` (an alias of ROM1, higher
   priority than the mirror). How the real chip select maps it is not known (see "Open questions").
3. **Flash ID.** `FE0C1BC0` compares the CFI/autoselect ID read from `0xF8000000` against `C2 25 38`, `20 BB 18`
   or `01 20 18` and asserts `Startup.c` line 220 (`0xDC`) otherwise. The 1300D answer is `C2 25 39`; the 4000D
   gets `C2 25 38` (Macronix, 128 Mbit = 16 MiB, consistent with item 1). This is the "FlashIF" blocker reported by
   the 2000D port.
4. **RTC oscillation adjust.** `rtc_time_correct = 0x31` (this ROM's `PROP_RTC`). With the 1300D's `0xFD` the
   firmware logs `RTC_TIME_CORRECT_CHANGE 0xfd ---> 0x31` and opens the Date/Time dialog instead of the shooting
   screen.
5. **current_task** is at `0x30978` (found by scanning RAM for pointers to DryOS task structures, name at +0x24;
   `-d tasks` then names every switch: DisplayMgr, PowerMgr, PropMgr, GuiMainTask, CtrlSrv...). Only used for
   logging.

Inherited unchanged from the 1300D (not individually re-verified): JPCORE status values, GPIO `0xC022F48C`
"System check" = HDMI disconnected, MPU request/status registers `0xC022D0C4` / `0xC022F484`, DryOS timer 1 /
interrupt 0x09, SD interrupts 0x4B / 0x32, UART RX 0x38, RTC CS `0xC022D0B8`.

## MPU

The 600D spell table (as used for the 1300D) is enough to boot to the GUI; the 1200D button codes drive the menu.
Spells the table does not answer (logged as `unknown`, boot is not affected): `PROP_VIDEO_MODE`
(`1a 18 01 4e ...`), `PROP_BURST_COUNT`, `PROP_AVAIL_SHOT`, `PROP_MPU_GPS`, `PROP 8003005A/5B`,
`PROP_USBDEVICE_CONNECT`, `06 05 04 1c`, `08 06 04 20`, `06 05 04 1f`.

## What works / what does not

| Works | Evidence |
|---|---|
| Bootloader → main firmware → `startupInitializeComplete` | UART: `K422 READY`, `[STARTUP] startupInitializeComplete`, `[MC] PROP_GUI_STATE 0` |
| Canon shooting screen (M mode, 0"3, F25, ISO AUTO, 35 shots) | frame `3020be96d6c022b4` |
| MENU (opens on the last tab: Wi-Fi ... "Versione Firmware 1.1.0"), → (My Menu), MENU (back) | frames in `bench/expected.json` |
| SD card mounted (shot count shown), Italian UI (settings stored in the ROM) | screenshots |
| `-d tasks`, `-d debugmsg` | as above |

Not working / not checked:
- `[SD] ERROR SDINTREP=0x00000000` / `UNEXPECTED ERROR` once at start-up (the card still mounts).
- `[PRP] ERROR ILLEGAL PARAM SIZE ID = 0x80010004`, `ConvertPropertyMovieDataToMovieSizeKind UnKnown MovieInfo`:
  property values come from the 600D spell table, not from a 4000D.
- LiveView, shooting, playback, power-management/idle behaviour: not looked at.
- `[CLKSAVER] ClockSaverExecute` repeats ~800 times per 30 s: the clock saver toggles `0xC0F01000/4`; harmless
  for booting, relevant for idle measurements.

## Timing (local build, `-O2`, no LTO, shared host with load average 10-20)

Boot to the shooting screen: 1.6-2.5 s wall in quiet runs, up to 5.8 s under heavy host load (guest-side the
display turns on at ~1.4-1.6 s DryOS time in every run: the variance is host contention). MENU / → / MENU
scenarios: 0.2-0.6 s each. Peak RSS ~110 MiB. The 1100D smoke test was re-run on the same build and still
matches its reference frames. CI numbers: see the `smoke-4000D/result.json` artifact.

Before the GUI the screen shows a grey frame with a few garbage pixels (`c56a6234e08ddaf6`) for 1-5 s; the smoke
test therefore waits for the GUI hash instead of the first stable frame.

## Open questions and useful captures from the real camera

All of these are read-only (logging to the SD card, no flash writes):
- **MPU spell log at boot** (ML `mpu_dump`/io_trace style logging of `mpu_send`/`mpu_recv` to a file): replaces
  the borrowed 600D table, fixes the `unknown` spells and the property errors, and gives the real button codes.
- **Reads of `0xFFFF0000-0xFFFF00FF` and `0xF8010000-0xF80100FF`** from a running camera (a small RAM dump to
  SD): shows whether the boot block really appears at hivecs after reset or whether the mapping changes once
  the bootloader runs.
- **Flash autoselect ID** as returned by the camera (log the three halfwords at `FE0C1BC0`'s caller) to confirm
  `C2 25 38`.
- **RTC register dump** (oscillation adjust register) to confirm `0x31`.
- **SD controller register log** during card init, to explain `SDINTREP=0`.
